# XTSY AI Intelligence v1 — deployment and operating notes

## What changes in this release

- The current browser-side deterministic parser and itinerary engine remain in place.
- A server-side OpenAI Responses API interpretation step adds better natural-language intent extraction, multilingual input understanding, conversational question handling and trip-edit normalization.
- Every itinerary is still generated by the existing deterministic `respond()` / `buildPlan()` engine. The LLM does not invent the final route, book services or confirm availability.
- If the model endpoint is missing, unavailable or rate-limited, the browser falls back to the existing deterministic assistant.
- Destinations outside XTSY's own Shillong cluster are disclosed as needing Booking Desk verification because this repository does not yet contain a live verified-Operator directory.
- The guest's trip enquiry remains pending. A separate Edge Function sends a Booking Desk review email to the fixed recipient configured in the template (`booking@xtsy.one`).
- The guest is told that a trip is submitted for verification, not booked or paid.

## Supabase secrets

Set the OpenAI API key as a server-side Supabase secret. Do not expose it through a `VITE_*` variable or commit it to Git.

```bash
Create a local environment file outside the Git working tree with the OpenAI key and a long random rate-limit salt. Then upload it with:

```bash
supabase secrets set --env-file /secure/path/xtsy-ai-secrets.env
```

Set `XTSY_AI_MODEL=gpt-6-luna` in that file as well if you want to pin the model explicitly.
```

The Edge Function defaults to `gpt-6-luna` when `XTSY_AI_MODEL` is not set. Confirm the model is enabled for the OpenAI API project used by XTSY.

## Deploy order

1. Apply the SQL migration `20261104150000_xtsy_ai_rate_limits.sql`.
2. Deploy `xtsy-ai-assistant` and `request-trip-verification`.
3. Deploy the email template registry update and `admin-trip-plan-review.tsx` with the existing `send-transactional-email` function.
4. Deploy the frontend feature branch after build and lint checks pass.

## Rate limits

- AI interpretation: 30 requests per IP per rolling hour.
- Booking Desk review request: 10 requests per IP per rolling hour.
- Only a salted hash of the selected proxy IP header is stored. No raw IP address is persisted by this limiter.
- If the rate-limit database is unavailable, the AI endpoint fails closed and the client uses its deterministic planner fallback. The Booking Desk review endpoint does not claim notification success.

## Important product boundary

The current Operator coverage layer is deliberately conservative. It does not query a live Operator registry because one does not yet exist in this branch. It labels destinations outside XTSY's Shillong cluster as requiring Booking Desk coverage verification. Once the verified-Operator registry exists, replace this conservative helper with a query against active, approved, destination-scoped Operators.

No road-closure feed, live weather provider, live ILP/PAP application interface, real-time partner inventory or multi-provider split settlement is added by this AI-intelligence release.

## Manual validation checklist

- Enter a free-text multi-destination itinerary and verify the AI normalizes it before the existing planner generates the day-by-day plan.
- Change the number of days, add a destination and remove a destination in separate follow-up messages.
- Ask a known XTSY question (such as current direct dorm rates) and confirm the curated local answer is retained.
- Ask an open-ended travel question and confirm the AI answers without claiming live availability or live conditions.
- Remove the OpenAI secret in a non-production environment and verify the existing deterministic planner still responds.
- Generate a trip containing destinations outside the Shillong cluster and confirm the coverage-verification note appears.
- Submit an enquiry with a test email and verify the `tour_enquiries` row remains pending and the Booking Desk review email is queued to `booking@xtsy.one`.
- Simulate email-queue failure and verify the guest is not told that the Booking Desk was successfully notified.
- Verify no screen says a booking is confirmed until the Booking Desk actually confirms it.
- Confirm that repeated API calls are rejected after the configured rate limit is reached.

## Multilingual boundary in this version

The model can interpret non-English requests. Open-ended question responses may use the detected reply language, but all deterministic planner summaries, itinerary cards, route labels and day-by-day stops remain English in this release. Full itinerary translation, voice STT/TTS and human-language Operator assignment remain later phases.
